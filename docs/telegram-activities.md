# 测试卡活动（无数据库）

## 管理方式

进入后台 **Telegram 客服 → 活动设置**。页面复用现有后台入口 `telegram.php?view=activities`，不新增 Nginx 路由，改名 admin 文件夹后链接仍由 App 生成。

1. 默认预设「领取单透测试卡」，先保存，默认暂停。
2. 导入卡密，一行一张，每次最多 1000 张。库存只在服务器私有状态中保存，页面导入后清空文本框；登录管理员可在「库存卡密明细」展开查看完整卡密，页面禁止缓存。
3. 勾选「开启领取入口」，保存。用户发送 `/start` 后，欢迎卡片在问题咨询 / 合作咨询下增加一个「🎁 领取单透测试卡」消息内按钮。保存不会群发。
4. 随时补充库存，重复或已分配过的卡会跳过；本活动库存记录上限 10,000 张。
5. 库存明细支持按状态筛选、每页 50 张；点击「删除此卡」或勾选后「删除勾选卡密」，确认后仅移除未分配库存，保留活动配置。已分配卡继续保留用于用户再次取卡。删除与领取共用排他锁，若选中的卡已被领取，整批删除取消并提示刷新。未分配卡删除后可以重新导入。
6. 暂时关闭：点击「暂停领取」。保留库存和限领，新欢迎卡片隐藏按钮，旧按钮提示活动已暂停或结束，不再发卡。
7. 永久结束：输入「删除活动」并确认。删除当前配置及库存原文，不撤回已发 Telegram 消息；已分配卡 SHA-256 指纹和近期每日限领记录保留，防止删除重建后重复发卡。新活动使用不同随机标识，旧按钮不领取新库存。

真实卡密不要写入源码、测试、日志、公开部署包或 Git。服务器备份若包含卡密，沿用私有配置备份权限；删除线上活动不自动删除历史备份。

## 领取规则

- 一个 Telegram 数字 ID 每个北京时间自然日限领 **1 张两小时卡**。北京时间 00:00 重置，而非滚动 24 小时。更改用户名不重置；多个账号视为不同用户，不承诺识别同一自然人。
- **实际两小时激活 / 到期由原卡密系统控制**；导入前应确认卡本身是两小时卡。机器人不解析或改变卡有效期，也不验证外部卡系统可用性。
- 当天再次主动点击，只展示分配给该用户的同一张卡，不增加使用时长或消耗新卡；库存为空时不消耗领取资格。
- 只接收该机器人本人私聊消息中的按钮，点击用户必须和私聊 ID 一致。不接受群组、其他机器人、伪造来源或未知按钮格式。已有屏蔽、每分钟限流和 Webhook secret 校验照常生效。
- 卡只发送给点击者；后台记录用户数字 ID、领取日期、卡片指纹和发送状态，完整卡仅在登录后的库存明细中查看。管理者主动点击正式领取按钮也会领取、消耗一张真实卡。

## 并发与异常

库存、限领、WebHook 去重共用 `TelegramStore` 排他文件锁。先原子记录“卡已归该用户 / 当日已领”，再调用 Telegram。并发点击同一用户不会分配多张，不同用户不会获得相同库存项。

确定的 429 重试继续发送原已预留卡，即使跨过北京时间零点也不换新卡。重复更新不会重发已确认消息。网络超时或进程在发送中断时保留卡所有权、标为待确认，不自动退回库存或重复发送；用户当天主动再次点击可以取回原卡。后续重显失败不会把之前已确认发送降级。

卡发出后用户屏蔽机器人、卡自身无效等情况也不把已分配的卡转给另一个用户。更换机器人或管理员绑定时保留库存、每日限领与已分配指纹，同时暂停活动，管理员核对后自行开启。

每日限领最多保存 20,000 项，领取时清理超过 8 天的历史记录；已分配卡指纹最多 100,000 项，达到上限停止新分配，不淘汰旧指纹以免重复导入。活动删除不清空当天额度。

```sh
php tests/telegram-trials.php

PHP_BINARY=php python3 tests/telegram-http.py

```

测试仅使用虚拟卡和注入的假 Telegram API，覆盖并发、跨日、重复请求、发送失败、暂停删除、旧按钮、CSRF、登录保护、库存保密和现有客服回归。生产部署只替换代码，保留原 `storage/telegram/state.json` 和 Token/Webhook 配置。
