# Telegram 公告卡片与定时删除

现有密码后台 → Telegram 客服 → **公告卡片**。不增加账号或数据库，同一机器人同时处理私聊客服和群组 / 频道公告。一次管理一张公告、一个投递位置；支持随时改文案或目标。

## 卡片编辑

- 预置用户提供的防骗声明正文；第三方示例账号不作为你的官方联系方式。唯一客服、双向联系用户名需要你填写，可留空隐藏。
- 正文支持 `**加粗**` 和 `*倾斜*`，换行直接保留；普通 HTML 按文字显示，不执行。正文与联系方式合计按 UTF-16 计数至多 4096，emoji 可能占两个单位。
- 两个底部按钮分别填写名称和 HTTPS 链接；地址留空隐藏。只生成 Telegram 原生 `inline_keyboard`，不下载链接内容。预览仅为示意，真实样式由 Telegram 客户端决定。
- 先保存，再“发给我测试”（仅发给已绑定的管理员），最后“立即投递”。表单未保存的修改不会用于发送；脚本启用时会暂时禁用发送按钮直到保存。测试消息也使用当前自动删除配置。
- 保存本身不发送消息。定时发送和自动删除默认都关闭，彼此独立。

使用官方 [sendMessage / 格式化说明](https://core.telegram.org/bots/api#sendmessage) 和 [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton)。本版本不依赖 Telegram 客户端的聊天自动删除功能。

## 目标与权限

1. 先完成 [机器人连接](telegram-support.md)，管理员先给机器人点 Start。
2. 将机器人加入你管理的群组 / 频道，授予发消息与删除消息的对应权限。频道建议设置为有发布 / 删除消息权限的管理员。
3. 填目标的 `@频道用户名` 或负数数字 chat ID（常见超级群 / 频道是 `-100…`）。个人正数 ID 不接受。
4. 每次投递前服务通过 `getChat` 核对类型并取得稳定的负数 chat ID。即使填写的用户名指向个人也不发送；实际删除沿用发送时解析的数字 ID，不随之后修改用户名 / 目标而变化。
5. 私有群 / 频道用负数 ID，不用邀请链接。可由已有管理工具获取；当前客服 Webhook 继续忽略群组、频道消息，不采集群聊来自动发现 ID。

## 定时发送

- **只发送一次**：到首次时间执行一次，然后关闭定时开关。
- **按间隔重复**：5 分钟至 30 天。首次时间可选；留空从保存时起延后指定间隔。时间采用北京时间（Asia/Shanghai），内部保存 Unix 时间。
- 再次保存会重排下一次发送，取消尚未发出的重试；已经成功发出的消息及删除计划保留不变。
- 停机后恢复最多补发当前一次，不追赶遗漏的多个周期。
- “暂停定时发送”同时取消尚未发送的重试；已经发送的公告仍按原计划删除。
- 在连接页暂停机器人会停止新公告与客服收发，但服务器脚本仍清理已经发送的公告；重新启用后尚未关闭的定时设置会恢复。

## 发送后自动删除

- 1 分钟至 **47 小时**，由服务器定时脚本调用 Telegram `deleteMessage`。每分钟运行时通常有约 0–60 秒调度误差，排队、网络或停机可能延迟。
- 仅清理本公告面板发送的消息（含管理员测试），不碰用户消息或客服回信。不需要清理时保持关闭。
- 改保留时长 / 关闭删除只影响后续新消息，旧消息保留发送时的计划。
- Telegram 普通删除接口要求消息发送未满 48 小时，并受机器人权限等条件限制。超过时限标记“已超过删除时限”，权限失败保留记录供管理员手动核对。详见 [deleteMessage 官方文档](https://core.telegram.org/bots/api#deletemessage)。
- 系统不承诺在断网 / 服务器停机时准点消失。若发送成功但回执丢失，系统没有消息 ID，需管理员在 Telegram 核对和手动处理。

## 安装服务器定时任务（必需）

仅双向客服不需要定时任务；**本页的定时发送 / 自动删除需要每分钟执行脚本**。没有新增 HTTP 定时接口，不靠访问页面触发。

宝塔：计划任务 → Shell 脚本 → 每分钟；命令示例：

```sh
cd /srv/mtx && /usr/bin/php bin/telegram-tick.php
```

通用 Linux crontab 示例在 `deploy/telegram-cron.example`。使用与 PHP-FPM 相同的系统用户和同一份 `config.local.php`、storage；CLI PHP 需 8.3+、curl、mbstring，保持出站 HTTPS TLS 校验。不要把 Token 写到命令行、URL 或 crontab。按实际安装目录调整路径。

后台显示最近运行时间；超过 3 分钟提示脚本未运行 / 停止。脚本只输出处理数量，失败返回非零退出码和通用提示；按服务器习惯配置日志轮转和失败监控。一次最多处理 10 个动作，动作之间释放锁，软时间预算约 30 秒（在途请求可能超出）。多进程共用同一文件锁和意图记录，避免重复投递。

更新 Nginx 白名单：新增 `/<随机入口>/admin/telegram-announcements.php` 以及 `/<随机入口>/assets/telegram-announcements.js`，参照最新模板。后台与接口继续使用既有随机入口和密码，不开放旧根路径。

## 文件、重试与更换机器人

同一私有文件 `storage/telegram/state.json` 的 announcements 部分保存卡片配置、投递 / 删除记录与运行时间。API 响应正文不保存；尚未完成的发送保留公告快照，完成后删除快照。已完成记录最多保留 100 条，活动任务最多约 1000 条；只有一个当前卡片配置。客服聊天正文仍不落盘。

- 手动按钮使用请求随机号去重，双击 / 近期 POST 重放不重复发同一条。
- 429 或只读目标解析超时最多重试 5 次，间隔至少 60 秒并遵守 Telegram retry_after。
- 发送前落盘 `pending`。发送超时 / 5xx / 崩溃后，结果记为“待确认”，不盲目重发，正式公告的定时设置同时暂停；管理员测试失败不改变频道定时开关。
- 删除超时可有限重试；如果实际已经删除但未收到回执，后续 API 可能返回 400，此时标记失败并提示人工核对，而非误报成功。
- 正在等待自动删除时，更换 Token / 管理员会提示先完成清理，以免用新机器人清理旧消息。删除失败、过期的消息应在 Telegram 人工处理。
- 首次绑定机器人保留提前编辑的草稿，但不自动开启定时；已有绑定更换身份则清空旧公告配置、记录和客服关联。
- 部署包不携带 Token / 公告运行数据。升级保留服务器的 config.local.php 和整个 storage，切勿用首次部署包覆盖已有数据。

## 验收

```sh
php tests/telegram-announcements.php
PHP_BINARY=php python3 tests/telegram-http.py
node tests/telegram-announcements-ui.test.cjs
```

全部使用临时目录、假 Telegram 传输或本机 HTTP，未向真实用户发消息。上线后由管理员填写真实账号和按钮，配置 HTTPS / Nginx / CDN 与定时脚本，再测试“发给我测试 → 自动删除 → 群组 / 频道投递 → 定时”全流程。
